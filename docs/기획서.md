## 01. 문제: 발견은 1초, 구매는 끝나지 않는다

핀터레스트에서 좋아요를 누르고, 인스타 룩을 캡처한다. 그런데 그 사진들은 대부분 앨범에 쌓인 채로 끝난다. 사고 싶은 마음은 있는데, 사는 과정이 너무 길다.

> "이 옷 어디 거예요?" 인기 룩 게시물마다 달리는 댓글. 답은 대부분 오지 않는다.

| | 불편 | 설명 |
| --- | --- | --- |
| 1 | 찾기가 어렵다 | 댓글을 뒤지거나, 상의·하의·신발을 하나씩 따로 검색해야 한다 |
| 2 | 결제가 흩어져 있다 | 한 룩의 아이템이 서로 다른 쇼핑몰에 있어 결제를 몇 번씩 반복한다 |
| 3 | 사이즈가 불안하다 | 브랜드마다, 남녀마다 사이즈가 달라 반품이 잦다. 패션 이커머스의 가장 큰 비용이기도 하다 |
| 4 | 예산이 안 맞는다 | 사진 속 룩은 비싸고, 비슷한 걸 더 싸게 찾는 데 또 시간이 든다 |

**해결:** 룩 사진을 올리면 에이전트가 **원본을 먼저 찾고**, 내 사이즈와 예산에 맞춰 여러 쇼핑몰 주문을 승인 한 번으로 끝낸다. 사지 않은 것은 계속 지켜본다.

## 02. 서비스 흐름: 사진 한 장에서 결제까지

사용자가 하는 일은 사진을 보내고 마지막에 승인하는 것뿐이다.

| 단계 | 누가 | 이름 | 내용 |
| --- | --- | --- | --- |
| 0 | 사용자 | 처음 설정 | 마이페이지에 성별, 키·몸무게, 평소 사이즈, 체형, 선호 핏·스타일·브랜드 입력 |
| 1 | 사용자 | **룩 모으기** | 갤러리에 쌓아둔 룩 사진을 **여러 장 한 번에 업로드**, 핀터레스트·인스타 게시물은 **공유하기**로 보냄. 모은 룩이 취향 분석의 중심 데이터 |
| 2 | 에이전트 | 룩 분해 | 사진 속 상의·하의·신발·가방을 인식, 옷장에 있는 건 제외 |
| 3 | 에이전트 | 원본 찾기 | 원본을 우선 찾고, 없거나 예산을 넘으면 대체 후보 2–3개 |
| 4 | 에이전트 | 사이즈 맞춤 | 성별 사이즈표, 실측표, 반품 이력으로 브랜드별 사이즈 선택 |
| 5 | 에이전트 | 예산 맞춤 | 룩 전체 예산과 아이템별 최대 금액 안에서 취향 점수가 가장 높은 조합 |
| 6 | 사용자 | 결제 방식 선택·승인 | 4가지 방식 중 고르고 총액을 보고 승인 |
| 7 | 에이전트 | 지켜보기 | 가격 하락, 품절 임박, 원본 재입고를 계속 감시 |

### 원본은 어디서 찾나

1. **핀의 출처 링크:** 원래 쇼핑몰 상품 페이지면 바로 원본
2. **국내 쇼핑몰:** 비전 LLM이 만든 검색어로 쇼핑 검색 API(예: 네이버 쇼핑 검색 API)
3. **전 세계 웹:** 구글의 이미지 검색 API(Cloud Vision 웹 감지)로 해외 브랜드까지
4. **확인:** 찾은 상품 사진을 이미지 유사도로 비교해 원본인지 대체 후보인지 판정

못 찾으면 솔직하게 알리고 대체 후보를 보여주며, 원본 재입고를 감시한다. 사용자가 늘면 패션 플랫폼 제휴로 자체 상품 DB를 만든다.

### 핵심 기능 예시: "내 깔인데, 더 싸게"

예산 15만 원으로 룩을 맞추는 경우. 존재감이 큰 신발은 원본 그대로, 비슷한 대체품이 많은 니트와 데님은 취향이 겹치는 저렴한 아이템으로 바꾼다. (금액은 설명용 예시)

```
LOOK #024 · PINTEREST              budget 150,000
-------------------------------------------------
crop knit / M→L                       189,000 (원본)
  ↳ swap · 92% match                   42,000
wide denim / 27                       129,000 (원본)
  ↳ swap · 88% match                   39,900
loafer / 245                           59,000
shoulder bag                          -- owned
-------------------------------------------------
original look                         377,000
TOTAL · 3 shops                       140,900
```

## 03. 핵심 기능

| 기능 | 무엇을 하나 | 예시 |
| --- | --- | --- |
| 마이페이지 | 성별(성별별 사이즈표), 신체 정보, 체형, 선호 핏·스타일·브랜드 | 남성 선택 → 상의 S–XXL, 하의 29–34, 신발 255–280 |
| 룩 분해 | 사진 한 장에서 아이템을 자동으로 나눠 인식, 옷장 중복 제외 | 사진 1장 → 니트, 데님, 로퍼 (가방은 이미 있음) |
| 원본 우선 찾기 | 출처 링크 → 국내 → 해외 순서로 원본 탐색 | "원본 상품을 모두 찾았어요" |
| 사이즈 맞춤 | 실측표와 반품 이력으로 브랜드별 사이즈 | "이 브랜드 M은 작았어요. L로 골랐어요." |
| 대체 후보 여러 개 | 아이템마다 2–3개, 이유가 다른 후보 | 추천 · 최저가 · 핏 가장 비슷 · 묶음배송 |
| 상품 상세 | 상세 이미지 5장, 두께·신축성·비침, 내 옷과 실측 비교, 리뷰 요약 | "정사이즈 58% · 나와 체형 비슷한 리뷰" |
| 룩 모으기 | 갤러리 사진 여러 장 업로드, 핀터레스트·인스타 공유하기. 옷이 없는 사진은 자동으로 제외 | 12장 업로드 → 패션 사진 11장 인식, 취향 업데이트 |
| **저장한 룩 기반 취향 (핵심)** | 내가 계속 캡처하고 저장해온 룩 사진들로 "내 감성"을 학습해, 대체 후보를 그 기준으로 고름 | 저장한 룩 24개 → 크롭 기장·아이보리·와이드 실루엣 선호 |
| 리뷰 기반 취향 (보조) | 내 후기·반품 사유·관심 상품 리뷰에서 좋아하는/피하는 포인트 추출 | 좋아함: 도톰한 소재 · 피함: 까슬한 소재 |
| 예산·사이즈·핏 조절 | 룩 전체 예산 + 아이템별 최대 금액·사이즈·핏 | "니트는 5만 원까지, 오버핏이라 L → XL" |
| 결제 방식 4가지 | 한 번에 결제 · 골라서 결제 · 장바구니에만 담기 · 가격 내려가면 사기 | 아래 05번 |
| 지켜보기 | 가격 하락, 품절 임박, 원본 재입고 | "L 사이즈 3개 남았어요" |
| 원본으로 바꾸기 | 대체품을 산 뒤 원본이 싸지면 반품과 원본 구매를 한 번에 제안 | 반품 기한·배송비·추가 금액을 계산해 이득일 때만 |

## 04. 차별점: 추천 앱은 보여주고 끝, 에이전트는 대신 끝낸다

| 기능 | 이미지 검색 렌즈 | 패션 플랫폼 스냅 | snap to buy |
| --- | :---: | :---: | :---: |
| 사진으로 상품 찾기 | ● | ◐ | ● |
| 룩 전체 한 번에 분해 | ◐ | ● | ● |
| 내 사이즈·체형 맞춤 | ○ | ◐ | ● |
| 예산 맞춤 대체품 | ○ | ○ | ● |
| 여러 쇼핑몰 한 번에 결제 | ○ | ○ | ● |
| 앱을 꺼도 가격·재고 감시 | ○ | ○ | ● |

● 지원 · ◐ 일부 지원 · ○ 미지원 (팀에서 실제 서비스를 사용해 보고 보완 예정)

**우리의 강점: "비슷한 옷"이 아니라 "내 감성의 옷"**

원본을 못 찾았을 때 비슷한 옷을 보여주는 서비스는 많다. snap to buy는 **내가 스크린샷과 핀으로 계속 저장해온 룩**을 취향 데이터로 쓴다. 저장한 룩이 쌓일수록 "이 사진과 비슷한 옷"이 아니라 **"이 사진 속 옷 중에서 내 감성에 맞는 옷"**을 고른다. 구매·반품·리뷰는 이 취향을 보정하는 보조 데이터다.

| 취향 데이터 | 비중 | 이유 |
| --- | --- | --- |
| 저장한 룩 (스크린샷, 핀) | **주** | 사용자가 매일 자연스럽게 쌓는 "좋아하는 것"의 가장 직접적인 기록 |
| 구매·유지·반품 | 보정 | 실제로 사서 입은 것과 맞지 않았던 것 |
| 리뷰 키워드 | 보정 | 소재·핏처럼 사진만으로 알기 어려운 선호 |

**왜 에이전트인가**

1. **연결된 여러 단계:** 니트를 바꾸면 남은 예산이 바뀌고 데님 후보도 바뀐다. 서로 영향을 주는 판단을 이어간다.
2. **보여주지 않고 행동한다:** 여러 쇼핑몰에 대신 주문한다. 사용자가 정한 한도 안에서, 승인 후에만.
3. **앱을 꺼도 일한다:** 가격 하락과 품절 임박을 며칠씩 지켜보다가 조건이 맞으면 사거나 알린다.
4. **막히면 스스로 푼다:** 품절, 사이즈 없음, 결제 실패에도 대체 후보를 찾거나 필요할 때만 묻는다.

**범용 에이전트(메타 Muse, Minds)와의 관계:** 범용 에이전트는 "이거 사줘"까지 한다. 브랜드별 사이즈, 반품 이력, 룩 단위 예산은 패션 데이터가 있어야 한다. snap to buy는 패션 전문 에이전트이며, 범용 에이전트가 부르는 패션 도구가 될 수도 있다.

## 05. 아키텍처: 누가 무엇을 하나

구글 클라우드 파트너 세션의 에이전트 구조를 snap to buy에 맞게 다시 그렸다. **무엇을 살지는 snap to buy가 정하고, 대신 실행하는 일은 Minds가, 그 권한이 안전한지는 AIR가 확인한다.**

```
[사용자] 핀 공유 · 결제 수단 연결 · 총액 승인
   │
   ▼
[snap to buy · Google Cloud]
   앱 → 오케스트레이터 에이전트 (Cloud Run · ADK · Gemini)
        ├─ 룩 분해   ├─ 상품 검색   ├─ 사이즈·취향   └─ 예산 조합
   │ A2A로 쇼핑몰 구매 에이전트 찾기 (Agent Registry)
   ▼
[AIR] 위임장(한도·허용 쇼핑몰·15분) · 에이전트 신원 검증 · 자격증명
   │
   ▼
[Minds] 구매 에이전트(주문 실행, 재고 재확인) · 감시 에이전트(가격·품절·재입고)
   │
   ▼
[외부] 쇼핑몰(공식 API · UCP 상품 데이터) · 카드사·PG(실제 결제)
```

| 담당 | 하는 일 |
| --- | --- |
| snap to buy | 룩 분해, 원본·대체 후보 찾기, 사이즈·예산·취향 맞춤, 주문 계획 |
| AIR | 위임장 발급, 에이전트 신원 검증, "L 사이즈 적합: 네" 같은 자격증명 |
| Minds | 승인된 주문 실행, 가격 하락·품절 임박·재입고 감시 |
| 카드사·PG | 실제 돈 이동. 국내는 카드 결제로 시작 |

**모델 구분:** 룩 분해(비전 모델), 상품 매칭(이미지 임베딩 + 벡터 DB), 취향 점수(저장한 룩 사진들의 임베딩으로 만든 "내 취향 벡터"와 후보의 거리, 구매·반품·리뷰로 보정), 예산 조합(최적화 계산)은 전용 모델과 알고리즘이 하고, LLM 에이전트는 도구를 언제 쓸지 정하고 이유를 설명한다.

## 06. 결제: 어디까지 맡기고 누가 승인하나

### 결제 방식 4가지

| 방식 | 동작 |
| --- | --- |
| 한 번에 결제 | 여러 쇼핑몰 주문을 승인 한 번으로 동시에 |
| 골라서 결제 | 체크한 아이템만 결제, 나머지는 찜하고 가격 감시 |
| 장바구니에만 담기 | 사이즈까지 맞춰 각 쇼핑몰 장바구니에 담기만, 결제는 직접 |
| 가격 내려가면 사기 | 목표가 이하에서 자동 결제. 품절 임박 기준(내 사이즈 5·3·1개 이하)과 그때 할 일(알림만 / 1만 원 더 비싸도 사기)을 미리 정함 |

### 결제 5단계

| 단계 | 담당 | 내용 |
| --- | --- | --- |
| 1 의도 정리 | snap to buy | 룩을 쇼핑몰별 주문으로 나눔 |
| 2 위임장 발급 | AIR | 사용자가 총액을 보고 승인하면 한도·허용 쇼핑몰·15분 유효 위임장 (AP2 방식) |
| 3 재고·가격 재확인 | Minds | 결제 직전 각 쇼핑몰 재고와 가격 재확인 (UCP) |
| 4 검증 | AIR | 위임장 범위를 벗어난 주문은 코드 규칙으로 차단 |
| 5 결제 | Minds → 카드사 | 국내 카드 결제 |

- **개인정보:** 쇼핑몰은 키·몸무게 대신 "L 사이즈 적합: 네"와 배송지만 받는다.
- **법적으로 안전한 구조:** 우리가 돈을 직접 받지 않고(쇼핑몰 결제창·등록 PG), 카드 번호는 저장하지 않으며(빌링키), 제휴 쇼핑몰의 공식 API로만 주문한다.
- **원본으로 바꾸기:** 대체품을 산 뒤 원본 가격이 내리면, 반품 기한·반품 배송비·추가 금액을 계산해 이득일 때만 "대체품 반품 + 원본 구매"를 제안하고 승인 시 한 번에 처리한다.
- **현실 점검:** Minds의 결제 기능은 공식 사이트 기준 "앞으로의 방향"이며, Minds × VISA 홍콩 실증은 파트너 세션에서 소개된 사례다. 국내 적용은 확인이 필요하다.

## 07. 수익 모델: 사용자는 무료, 수익은 판매자에서

| 수익원 | 방식 |
| --- | --- |
| 제휴 수수료 | 구매 1건당 일정 비율. 사이즈 추천으로 반품이 줄어드는 만큼 판매자도 이득이다 |
| 추천 상품 광고 | 룩 분해 화면 상단에 "광고" 표시 상품. 원본을 가리지 않도록 한 줄만 |
| 크리에이터 제휴 | 인플루언서가 룩의 아이템을 직접 등록하면 원본이 보장되고, 판매 수수료를 나눈다 |
| 트렌드 리포트 | 많이 저장되고 팔리는 룩을 익명 통계로 브랜드에 제공한다 |

## 08. 로드맵: 검색에서 시작해 에이전트로

1. **P1 · MVP (찾기):** 핀 공유·저장 연동 → 아이템 인식 → 원본·비슷한 상품 → 구매 링크·장바구니. 결제는 사용자가 직접.
2. **P2 · 맞춤 (사이즈와 예산):** 성별 사이즈표·실측 비교, 예산 맞춤 대체 후보, 리뷰 기반 취향. 구매·반품 데이터로 학습.
3. **P3 · 에이전트 (대리 결제·감시):** 제휴 쇼핑몰부터 위임 한도 안에서 대리 결제(AIR·Minds), 가격 감시 자동 구매, 원본으로 바꾸기.

핀터레스트 앱 안의 "바로 사기" 버튼은 핀터레스트 제휴가 필요하므로, 초기에는 공유하기와 저장 핀 연동으로 시작한다.

## 09. 예상 질문

| 질문 | 답변 방향 |
| --- | --- |
| 구글 렌즈랑 뭐가 달라요? | 렌즈는 찾아주는 데서 끝난다. 우리는 사이즈와 예산을 맞추고 대신 사고, 계속 지켜보는 에이전트다 |
| 원본을 못 찾으면요? | 출처 링크 → 국내 → 해외 순서로 찾고, 못 찾으면 솔직하게 알린다. 그때 대체 후보는 단순히 비슷한 옷이 아니라 **내가 저장해온 룩으로 학습한 내 감성** 기준으로 고르고, 원본 재입고도 감시한다 |
| 대체품 추천은 다른 데도 하지 않나요? | 다른 곳은 "이 사진과 비슷한 옷"을 찾는다. 우리는 사용자가 계속 저장해온 룩으로 "내 감성"을 학습해서 그 기준으로 고른다 |
| 메타 Muse가 하면 끝 아니에요? | 범용 에이전트는 "사줘"까지다. 브랜드별 사이즈, 반품 이력, 룩 단위 예산은 패션 데이터가 필요하다. 범용 에이전트가 부르는 패션 도구도 될 수 있다 |
| AI가 대신 결제하면 위험하지 않나요? | 총액 승인 후에만 한도·쇼핑몰·15분 제한 위임장이 발급되고, 범위를 벗어나면 코드 규칙이 막는다. 결제사와 구글도 같은 방식의 에이전트 결제 표준을 만들고 있다 |
| 사이즈는 어떻게 맞추나요? | 성별 사이즈표와 평소 사이즈로 시작하고, 실측 비교와 반품 이력이 쌓일수록 정확해진다 |
| 내 정보는 안전한가요? | 쇼핑몰에는 "L 사이즈 적합: 네"와 배송지만 공유하고(AIR 자격증명), 원본 사진은 저장하지 않는다 |
| 조건을 AI가 무시하면요? | 아이템별 최대 금액·사이즈·룩 예산은 하드 필터라 코드로 지킨다. 취향은 순서만 정하는 소프트 점수다 |
