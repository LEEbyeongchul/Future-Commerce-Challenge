## 1. README 초안

아래 내용을 그대로 `README.md`로 바꿔 넣는다.

```markdown
# snap to buy (가칭)

> 저장만 해두던 룩을, 오늘 주문하는 옷으로.

**▶ 목업 체험:** https://leebyeongchul.github.io/Future-Commerce-Challenge/mockup/
**Future Commerce Challenge 2026** · Track A. Future Shopping Experience

> 데모 범위: 목업의 브랜드·상품·가격·리뷰·쇼핑몰 이름은 모두 가상 예시입니다.
> 실제 AI 모델이나 결제와 연결되지 않은, 사용 경험을 보여주는 화면 시연입니다.

## 문제 정의
핀터레스트와 인스타에서 마음에 드는 룩을 저장하지만, 대부분 사지 못한 채 앨범에 쌓인다.
- 사진 속 옷이 어디 건지 찾기 어렵다
- 한 룩의 아이템이 여러 쇼핑몰에 흩어져 있다
- 브랜드마다 사이즈가 달라 반품이 잦다
- 사진 속 룩은 비싸고, 비슷한 걸 더 싸게 찾는 데 또 시간이 든다

## 주요 기능
| 기능 | 설명 |
| --- | --- |
| 룩 분해 | 사진 한 장에서 니트·데님·신발·가방을 아이템별로 인식 |
| 원본 찾기 | 핀의 출처 링크, 쇼핑 검색, 이미지 유사도로 원본 상품을 우선 찾음 |
| 사이즈 맞춤 | 마이페이지의 체형 정보와 구매·반품 이력으로 브랜드별 사이즈 추천 |
| 대체 후보 | 원본이 없거나 예산을 넘으면 취향이 비슷한 후보 2–3개와 핏·실측·리뷰 제공 |
| 예산 맞춤 | 룩 전체 예산과 아이템별 최대 금액·사이즈·핏을 지키는 조합 계산 |
| 결제 방식 선택 | 한 번에 결제 · 골라서 결제 · 장바구니에만 담기 · 가격 내려가면 사기 |
| 옷장 중복 체크 | 이미 가진 아이템은 구매에서 제외 |

## 서비스 흐름
영감 수집 → 룩 분해 → 원본 찾기·사이즈 맞춤 → 예산 맞춤 → 결제 방식 선택 → 완료

## 기술 구조
- **에이전트:** LLM이 요청을 해석하고 도구(룩 분해, 상품 검색, 취향 점수, 사이즈 추천, 예산 조합)를 순서대로 호출한다. 계산은 각 도구가 하고, LLM은 순서 결정과 이유 설명만 맡는다.
- **상품 검색:** 출처 링크 → 국내 쇼핑 검색 API → 구글 이미지 검색 API로 찾고, 이미지 유사도로 원본인지 확인한다. MVP는 상품 DB 없이 동작한다.
- **결제 안전장치:** 결제 여부는 LLM이 아니라 코드 규칙(한도·허용 쇼핑몰·사용자 승인)이 최종 확인한다. 권한 위임과 에이전트 신원 확인은 AIR Agent를 기준으로 설계했다.

## 미구현 범위
- 목업은 화면 시연이며, 실제 이미지 인식·상품 검색·결제는 구현하지 않았다
- 쇼핑몰 제휴와 실제 결제 연동은 없다
- 사이즈 추천과 취향 점수는 예시 값이다

## 로드맵
1. **MVP:** 사진 → 아이템 인식 → 원본·비슷한 상품 찾기 → 구매 링크 (결제는 사용자가 직접)
2. **맞춤:** 사이즈 추천, 예산 맞춤 대체 후보, 리뷰 기반 취향 분석
3. **에이전트:** 제휴 쇼핑몰부터 위임 한도 안에서 대리 결제

기획 정리, 문서 작성, 목업 코드 작성에 AI 코딩 도구(Claude Code)를 사용했다.
```

## 3. 예상 질문 추가: 대리 결제는 안전한가

**질문:** "AI가 대신 결제하면 위험하지 않나요?"

**답변:**
> "결제사 Adyen과 구글이 이미 에이전트 결제 규격을 만들고 있습니다. 저희도 같은 방식으로, 사용자가 **정확한 총액을 승인한 뒤에만** 권한을 넘깁니다. 이 권한은 **이번 결제 한 건에만, 정해진 금액까지, 해당 쇼핑몰에서만, 짧은 시간 동안만** 쓸 수 있습니다. AI는 카드 정보를 보지 않고, 결제 전에 재고와 가격을 다시 확인합니다."

**근거 메모**
| 근거 | 내용 |
| --- | --- |
| Adyen 에이전트 결제 규격(ACP) 시연 | 1회용 권한, 최대 금액 = 결제 총액, 해당 가맹점·결제 건에만 사용, 15분 만료, LLM은 결제 세션 ID만 받음 |
| 구글 ADK + AP2 실습 자료 | 구글이 에이전트 결제 규격을 개발자 실습 자료까지 내며 밀고 있음 |

**발표 전 확인:** ACP, AP2의 정확한 이름과 내용은 각 공식 문서로 한 번 확인한다.

## 4. 예상 질문 추가: 조건과 취향은 어떻게 다르게 처리하나

**질문:** "예산이나 사이즈 조건을 AI가 무시하면 어떡해요?"

**답변:**
> "조건은 두 종류로 나눠서 처리합니다. 사용자가 직접 정한 **아이템별 최대 금액, 사이즈, 룩 전체 예산**은 **하드 필터**라서 무조건 지킵니다. AI 판단이 아니라 코드 규칙으로 걸러냅니다. **취향**은 **소프트 점수**라서 후보의 순서만 정합니다. 그래서 AI가 취향을 잘못 판단해도 예산이나 사이즈를 어기는 일은 없습니다."

| 구분 | 예시 | 처리 |
| --- | --- | --- |
| 하드 필터 (무조건 지킴) | 니트 5만 원까지, 사이즈 L, 룩 전체 15만 원 | 조건에 안 맞는 상품은 후보에서 제외 |
| 소프트 점수 (순서만 정함) | 취향 일치도 92%, 리뷰의 "도톰해요" | 남은 후보 중 점수가 높은 순으로 추천 |

조건에 맞는 후보가 하나도 없으면, 목업처럼 "5만 원 안의 후보가 없어서 가장 저렴한 상품을 골랐어요"라고 솔직하게 알린다.

## 5. 결제 흐름 슬라이드 (파트너 세션 반영)

오늘 구글 클라우드·Animoca 파트너 세션의 "에이전트 결제 프로세스"를 우리 서비스 말로 옮긴 한 장짜리 슬라이드 문구다. 목업 결제 화면에도 같은 5단계를 넣었다.

**슬라이드 제목:** AI에게 어디까지 맡기고, 누가 승인하나

| 단계 | 화면에 쓸 문구 | 근거 (세션 내용) |
| --- | --- | --- |
| 1 의도 정리 | "이 룩 15만 원 안에서" → 쇼핑몰 3곳 주문으로 나눔 | 에이전트가 요청을 개별 거래로 분해 |
| 2 위임장 발급 | 사용자가 총액을 보고 승인 → 한도·허용 쇼핑몰·15분 유효 위임장 | AP2: 한도와 조건이 담긴 위임장 |
| 3 재고·가격 재확인 | 결제 직전 각 쇼핑몰 재고·가격 다시 확인 | UCP: 가맹점 연결, 재고 확인 |
| 4 검증 | 위임장 범위를 벗어난 주문은 자동 차단 | 위임장 대조, 이상거래 탐지 |
| 5 결제 | 국내 카드로 결제 | 정산 (국내는 카드·PG) |

**개인정보 한 줄:** 쇼핑몰은 키·몸무게 대신 "L 사이즈 적합: 네"만 받는다 (AIR 자격증명 방식).

**실현성 한 줄:** Minds가 주문하고 AIR가 신원을 검증해 매장 결제까지 끝내는 흐름이 홍콩 브랜드 3곳에서 이미 운영 중이다 (파트너 세션 소개 내용).

**발표 멘트 (20초):**
> "AI가 결제까지 하지만, 사용자가 총액을 보고 승인한 순간에만 위임장이 발급됩니다. 이 위임장은 정해진 금액, 정해진 쇼핑몰, 15분 동안만 쓸 수 있고, 쇼핑몰은 내 키와 몸무게 대신 '이 사이즈가 맞다'는 답만 받습니다."

**주의**
- AP2, UCP 같은 용어는 괄호 속 근거로만 쓰고, 설명은 사용자 말로 한다.
- 크립토 정산은 국내 제도가 불확실하니 강조하지 않는다.
- 용어와 사례는 파트너 세션 사진에서 읽은 것이라, 발표 전에 세션 자료로 한 번 확인한다.

## 6. 역할 분담: 누가 무엇을 하나 (Minds 반영)

| 역할 | 담당 | 하는 일 |
| --- | --- | --- |
| 무엇을 살지 정하기 | **snap to buy** | 룩 분해, 원본·대체 후보 찾기, 사이즈·예산·취향 맞춤 |
| 대신 실행하기 | **Minds** | 승인된 주문·결제 실행, 가격 하락·품절 임박·재입고 감시 |
| 믿을 수 있게 하기 | **AIR** | 위임장(한도·쇼핑몰·시간) 발급, 에이전트 신원 검증, "L 사이즈 적합: 네" 같은 자격증명 |
| 실제 돈 이동 | **카드사·PG** | 국내 카드 결제 |

**발표 멘트:** "무엇을 살지는 저희가 정하고, 대신 사고 지켜보는 일은 Minds가, 그 권한이 안전한지는 AIR가 확인합니다."

**주의:** Minds의 국내 결제 지원 범위는 확인되지 않았다. 세션에서 소개된 실증은 홍콩 사례다.
