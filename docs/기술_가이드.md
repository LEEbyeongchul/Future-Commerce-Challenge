# snap to buy 기술 가이드

이 앱을 실제로 만든다면 어떤 지식이 필요하고, 내부에서 어떻게 돌아가는지 정리한 문서다. 1장은 용어, 2–6장은 전문적인 구조, 7장은 기술 스택과 팀 구성이다. 특정 모델과 도구 이름은 대표적인 예시이고, 실제로는 비교해 보고 고른다.

---

## 1. 필요한 지식과 용어

### 1-1. 필요한 지식 분야

| 분야 | 왜 필요한가 | 이 앱에서 쓰이는 곳 |
| --- | --- | --- |
| 컴퓨터 비전 | 사진에서 옷을 찾아 잘라낸다 | 룩 분해 |
| 표현 학습 / 임베딩 | 이미지를 비교 가능한 숫자로 바꾼다 | 상품 매칭, 취향 점수 |
| 정보 검색 / 추천 시스템 | 수많은 상품 중 비슷한 것을 빠르게 찾고 순위를 매긴다 | 후보 검색, 재정렬 |
| LLM / 에이전트 | 사용자 말을 이해하고 도구를 순서대로 호출한다 | 오케스트레이터, 이유 설명 |
| 최적화 알고리즘 | 예산 안에서 가장 좋은 조합을 고른다 | 예산 조합 |
| 데이터 엔지니어링 | 상품 데이터를 모으고 정제해 계속 갱신한다 | 상품 수집 파이프라인 |
| 백엔드 / 분산 시스템 | 서버, DB, 작업 큐, 스케줄러 | 전체 서비스, 가격 감시 |
| 결제 / 핀테크 | PG, 빌링키, 정산 구조 | 결제 |
| 보안 / 개인정보 | 권한 관리, 암호화, 프롬프트 인젝션 방어 | 전체 |
| 모바일 / 프론트엔드 | 앱 화면, 사진 업로드, 공유하기 연동 | 클라이언트 |

### 1-2. 용어 사전

**AI·모델**

| 용어 | 뜻 |
| --- | --- |
| 객체 탐지 (Object Detection) | 사진에서 물체의 위치를 네모 상자로 찾아내는 기술 |
| 세그멘테이션 (Segmentation) | 물체의 윤곽을 픽셀 단위로 정확히 따내는 기술. 옷만 깔끔하게 잘라낼 때 쓴다 |
| 바운딩 박스 (Bounding Box) | 탐지된 물체를 감싸는 네모 상자 좌표 |
| 임베딩 (Embedding) | 이미지나 글을 수백 개 숫자로 된 벡터로 바꾼 것. 비슷한 것끼리 가까운 위치에 놓인다 |
| 벡터 (Vector) | 숫자의 나열. 예: [0.12, -0.53, 0.88, …] |
| 코사인 유사도 (Cosine Similarity) | 두 벡터가 얼마나 같은 방향을 보는지로 유사도를 재는 방법. 1에 가까울수록 비슷하다 |
| CLIP 계열 모델 | 이미지와 글을 같은 벡터 공간에 넣는 모델. "아이보리 케이블 니트"라는 글로 이미지를 찾을 수도 있다 |
| 파인튜닝 (Fine-tuning) | 이미 학습된 모델을 우리 데이터(패션 사진)로 추가 학습시키는 것 |
| 재정렬 (Re-ranking) | 1차로 빠르게 뽑은 후보를 더 정밀한 기준으로 다시 순위 매기는 것 |
| 콜드 스타트 (Cold Start) | 신규 사용자나 신상품처럼 데이터가 없어서 추천이 어려운 상태 |
| 비전 LLM (VLM) | 이미지를 보고 글로 답할 수 있는 LLM. 실측표 이미지 읽기, 속성 태그 추출에 쓴다 |

**에이전트·LLM**

| 용어 | 뜻 |
| --- | --- |
| LLM (Large Language Model) | 대규모 언어 모델. 글을 이해하고 생성한다 |
| 에이전트 (Agent) | LLM이 목표를 위해 스스로 도구를 골라 쓰고 여러 단계를 수행하는 구조 |
| 도구 호출 (Tool Use / Function Calling) | LLM이 "이 함수를 이 값으로 실행해줘"라고 요청하고, 결과를 받아 다음 행동을 정하는 방식 |
| 오케스트레이터 (Orchestrator) | 여러 도구와 단계를 지휘하는 중앙 에이전트 |
| 프롬프트 (Prompt) | LLM에게 주는 지시문과 입력 |
| 프롬프트 인젝션 (Prompt Injection) | 상품 설명 같은 외부 글에 숨은 지시를 넣어 LLM을 속이는 공격 |
| 가드레일 (Guardrail) | LLM이 하면 안 되는 행동을 코드 규칙으로 막는 안전장치 |
| 구조화 출력 (Structured Output) | LLM 답을 자유 문장이 아닌 정해진 JSON 형식으로 받는 것 |

**검색·데이터**

| 용어 | 뜻 |
| --- | --- |
| 벡터 DB (Vector Database) | 임베딩을 저장하고 비슷한 벡터를 빠르게 찾는 DB |
| ANN (근사 최근접 이웃) | 수백만 벡터 중 가장 가까운 것을 "거의 정확하게, 아주 빠르게" 찾는 방법 |
| HNSW | 가장 널리 쓰이는 ANN 인덱스 구조. 그래프를 타고 이동하며 가까운 벡터를 찾는다 |
| 메타데이터 필터 | 벡터 검색과 함께 "가격 5만 원 이하, 재고 있음, 사이즈 L 있음" 같은 조건을 거는 것 |
| ETL / 데이터 파이프라인 | 데이터를 가져오고(Extract), 정리하고(Transform), 저장하는(Load) 흐름 |
| 상품 피드 (Product Feed) | 쇼핑몰이 제휴사에 제공하는 상품 목록 데이터 (이미지, 가격, 재고 등) |
| 정규화 (Normalization) | 쇼핑몰마다 다른 형식을 하나의 공통 형식으로 맞추는 작업. 예: "Free", "F", "프리사이즈" → FREE |
| 배치 / 실시간 처리 | 정해진 시간에 몰아서 처리하는 것 / 요청이 오면 바로 처리하는 것 |

**최적화**

| 용어 | 뜻 |
| --- | --- |
| 배낭 문제 (Knapsack Problem) | 무게 제한 안에서 가치 합이 최대인 물건 조합을 고르는 문제 |
| 다중 선택 배낭 문제 | 그룹마다 하나씩 골라야 하는 배낭 문제. "아이템마다 원본 또는 후보 중 하나"가 정확히 이 구조 |
| 전수 탐색 (Brute Force) | 모든 조합을 다 비교하는 방법. 아이템 4개 × 후보 4개면 256가지라 순식간에 끝난다 |

**결제·인프라·보안**

| 용어 | 뜻 |
| --- | --- |
| PG (Payment Gateway) | 카드 결제를 대행하는 회사. 쇼핑몰과 카드사 사이를 연결 |
| 빌링키 (Billing Key) | PG가 카드 정보 대신 발급하는 결제용 토큰. 우리는 카드 번호를 저장하지 않는다 |
| OAuth | 비밀번호를 받지 않고 다른 서비스(Pinterest) 데이터 접근 권한만 받는 표준 방식 |
| 스코프 (Scope) | 권한의 범위. 예: 읽기 전용, 한도 30만 원 |
| 멱등성 (Idempotency) | 같은 요청을 두 번 보내도 결과가 한 번만 일어나는 성질. 결제 중복을 막는다 |
| 메시지 큐 (Message Queue) | 작업을 줄 세워 놓고 순서대로 처리하는 시스템. 오래 걸리는 작업을 분리한다 |
| 스케줄러 (Scheduler) | 정해진 주기로 작업을 실행. 가격 감시에 쓴다 |
| 웹훅 (Webhook) | 다른 서비스가 일이 생기면 우리 서버로 알려주는 방식. 예: 배송 출발 알림 |
| 감사 로그 (Audit Log) | 에이전트가 언제, 무엇을, 왜 했는지 남기는 기록 |

## 2. 시스템 아키텍처

### 2-1. 전체 구조

```
[클라이언트] 모바일 앱 / 웹 ── 사진 업로드 · 결과 화면 · 결제 승인
   │ HTTPS
   ▼
[API 게이트웨이] 로그인 확인 · 요청 제한 · 라우팅
   │
   ▼
[에이전트 오케스트레이터 · LLM] 요청 해석 → 도구 호출 → 결과 종합 → 이유 설명
   │
   ├─ 비전 서비스 ──────── 룩 분해
   ├─ 검색 서비스 ──────── 상품 매칭
   ├─ 취향 서비스 ──────── 취향 점수
   ├─ 사이즈 서비스 ────── 사이즈 추천
   ├─ 예산 최적화 ──────── 조합 계산
   └─ 커머스 커넥터 ────── 주문 · 장바구니
            │
            ▼
      [가드레일 · 코드 규칙] 한도 · 허용몰 · 승인 검사
            │
            ▼
      [외부 연동] 쇼핑몰 API · PG · AIR · Pinterest

[데이터 계층] 관계형 DB · 벡터 DB · 이미지 저장소 · 캐시   ← 각 서비스가 읽고 씀
   ▲
   │
[백그라운드] 상품 수집 파이프라인 · 가격 감시 스케줄러 · 학습 작업
```

### 2-2. 구성 요소별 역할

| 구성 요소 | 역할 | 입력 → 출력 |
| --- | --- | --- |
| 클라이언트 | 사진 업로드, 결과 표시, 결제 최종 승인 | 사용자 조작 → API 요청 |
| API 게이트웨이 | 로그인 확인, 요청 제한, 라우팅 | 요청 → 내부 서비스 |
| 오케스트레이터 | LLM이 도구를 호출하며 전체 흐름 지휘 | "이 룩 15만 원 안에서" → 최종 제안 + 설명 |
| 비전 서비스 | 옷 탐지·세그멘테이션, 크롭, 카테고리 분류 | 사진 → 아이템별 크롭 이미지 + 카테고리 |
| 검색 서비스 | 임베딩 생성, 벡터 DB 검색, 재정렬 | 크롭 이미지 → 원본/대체 후보 목록 |
| 취향 서비스 | 사용자 취향 벡터 관리, 후보별 취향 점수 | 사용자 ID + 후보 → 점수 |
| 사이즈 서비스 | 실측 비교, 반품 이력 반영 | 사용자 + 상품 → 추천 사이즈 + 근거 |
| 예산 최적화 | 다중 선택 배낭 문제 풀이 | 아이템별 후보 + 예산 → 최적 조합 |
| 커머스 커넥터 | 쇼핑몰별 API 차이를 감싸서 통일된 주문·장바구니 기능 제공 | 주문 요청 → 쇼핑몰별 주문 결과 |
| 가드레일 | 결제 전 한도·허용몰·금액을 **코드로** 최종 검사 | 주문 요청 → 통과/거부 |
| 가격 감시 스케줄러 | 찜·대기 상품 가격을 주기적으로 확인 | 감시 목록 → 알림 또는 자동 주문 요청 |
| 상품 수집 파이프라인 | 상품 피드 수집, 정제, 임베딩, 색인 | 쇼핑몰 데이터 → 검색 가능한 상품 DB |

### 2-3. 데이터 저장소

| 저장소 | 저장하는 것 | 예시 도구 |
| --- | --- | --- |
| 관계형 DB | 사용자, 주문, 상품 정보, 사이즈표, 권한, 동의 기록 | PostgreSQL |
| 벡터 DB | 상품 이미지 임베딩, 사용자 취향 벡터 | pgvector, Qdrant, Milvus |
| 객체 저장소 | 상품 이미지, 크롭 이미지 | S3 호환 스토리지 |
| 캐시 | 자주 보는 검색 결과, 세션 | Redis |
| 메시지 큐 | 이미지 분석·가격 확인 같은 비동기 작업 | Redis Queue, Kafka, Cloud Tasks |

## 3. 실제 가동 메커니즘: 요청 하나가 처리되는 순서

사용자가 룩 사진을 올리고 "15만 원 안에서 맞춰줘"를 누른 경우.

```
[사용자] 룩 사진 업로드, "15만 원 안에서"
   │
   ▼
[앱] 이미지 저장 → 오케스트레이터에 요청
   │
   ▼
[오케스트레이터 · LLM] 요청 해석, 도구 호출 계획
   │
   ├─ ① 비전 서비스 ─────── 옷 탐지·크롭 → 아이템 4개
   ├─ ② 검색 서비스 ─────── 아이템마다 원본 + 후보 (병렬)
   ├─ ③ 취향·사이즈 서비스 ── 후보별 점수, 추천 사이즈 (병렬)
   ├─ ④ 예산 최적화 ─────── 예산 안 최적 조합
   └─ ⑤ LLM 설명 생성 ────── "이 브랜드 M은 작았어요"
   │
   ▼
[앱] 제안 화면 → 사용자가 결제 방식 선택·승인
   │
   ▼
⑥ [가드레일 · 코드 규칙] 한도·허용몰·승인 여부 검사 ── 통과 못 하면 중단
   │
   ▼
⑦ [커머스 커넥터] 쇼핑몰·PG 주문 → 결과 알림 + 감사 로그 기록
```

| 단계 | 하는 일 | 목표 응답 시간 |
| --- | --- | --- |
| ① 룩 분해 | 탐지 모델로 옷 영역 찾기, 크롭, 카테고리 분류. 가방이 옷장에 있으면 제외 | 0.5초 이내 |
| ② 상품 검색 | 크롭 → 임베딩 → 벡터 DB에서 카테고리·재고 필터와 함께 상위 50개 → 재정렬 → 원본 1개 + 후보 3개 | 아이템당 0.3초 (병렬) |
| ③ 점수·사이즈 | 후보마다 취향 점수, 추천 사이즈와 근거 계산 | 0.2초 |
| ④ 예산 조합 | 모든 조합 비교 후 예산 안에서 점수 합 최대 조합 선택 | 0.01초 |
| ⑤ 설명 생성 | LLM이 "이 브랜드 M은 작았어요" 같은 이유 문장 작성 | 1–2초 (스트리밍) |
| ⑥ 가드레일 | 금액 ≤ 한도, 쇼핑몰 ∈ 허용 목록, 사용자 최종 승인 여부를 **코드로** 검사 | 즉시 |
| ⑦ 주문 | 쇼핑몰별 주문 API 호출, 실패 시 재시도(멱등키 사용), 결과 기록 | 쇼핑몰에 따라 다름 |

**핵심 설계 원칙:** LLM은 ①–④를 "언제 부를지"만 정하고, 계산은 각 서비스가 한다. ⑥의 결제 판단은 LLM이 아니라 규칙 엔진이 한다.

## 4. 데이터 파이프라인

### 4-1. 상품 수집 파이프라인 (오프라인, 매일·매시간)

```
쇼핑몰 상품 피드 / 검색 API
        │ ① 수집 (Extract)
        ▼
  원본 데이터 저장
        │ ② 정제·정규화 (Transform)
        │    - 카테고리 통일 (니트/스웨터/풀오버 → 니트)
        │    - 사이즈 표기 통일 (Free/F/프리 → FREE)
        │    - 중복 상품 제거 (같은 상품이 여러 몰에)
        │    - 실측표 이미지 → 비전 LLM으로 표 데이터 추출
        ▼
  ③ 이미지 처리
        │    - 대표 이미지에서 옷 영역 크롭
        │    - 임베딩 생성 (GPU 배치 작업)
        │    - 속성 태그 생성 (소재, 패턴, 기장, 색)
        ▼
  ④ 적재 (Load)
        - 관계형 DB: 상품 정보, 가격, 재고, 실측
        - 벡터 DB: 임베딩 + 필터용 메타데이터
```

| 주기 | 갱신 대상 |
| --- | --- |
| 매시간 | 가격, 재고 (가격 감시와 품절 처리에 필요) |
| 매일 | 신상품 추가, 단종 상품 제거 |
| 모델 교체 시 | 전체 임베딩 재생성 |

### 4-2. 사용자 데이터 파이프라인

```
모은 룩(갤러리 업로드 · 핀터레스트 공유 · 인스타 공유) · 구매 · 반품 · 리뷰 · 클릭
        │
        ▼
  이벤트 로그 저장 (누가, 언제, 무엇을, 어떻게 반응)
        │
        ├─▶ 취향 벡터 갱신: 모은 룩 사진(주 데이터)의 옷 임베딩 + 구매·리뷰로 보정
        │     (최근에 모은 룩일수록 높게, 구매·유지는 더하고 반품은 낮게)
        │
        └─▶ 사이즈 프로필 갱신: 잘 맞은 옷의 실측 범위, "작아서/커서 반품" 기록
```

### 4-3. 피드백 루프 (서비스가 똑똑해지는 구조)

```
추천 → 사용자 선택/무시 → 구매 → 유지/반품
  ▲                                      │
  └──── 취향 벡터·사이즈 프로필·재정렬 모델 갱신 ◀┘
```

쓸수록 쌓이는 데이터가 **경쟁사가 따라오기 어려운 해자**가 된다.

## 5. 모델과 알고리즘 상세

### 5-1. 룩 분해: 탐지 + 세그멘테이션

| 항목 | 내용 |
| --- | --- |
| 모델 예시 | YOLO 계열 탐지 모델, SAM 계열 세그멘테이션 모델 |
| 학습 데이터 예시 | 공개 패션 데이터셋(DeepFashion2, Fashionpedia 등)으로 파인튜닝 |
| 출력 | 아이템별 바운딩 박스, 마스크, 카테고리(상의/하의/신발/가방…), 신뢰도 |
| 어려운 점 | 겹친 옷(코트 안 니트), 가려진 신발, 액세서리처럼 작은 물체 |

### 5-2. 상품 매칭: 임베딩 + 벡터 검색 + 재정렬

```
크롭 이미지 → 임베딩 모델 → 벡터 (예: 512차원)
                                  │
                    벡터 DB 검색 (HNSW) + 필터
                    (카테고리 = 니트, 재고 있음, 내 사이즈 있음)
                                  │
                          상위 50개 후보
                                  │
                재정렬: 시각 유사도 + 속성 일치 + 가격 + 판매자 신뢰도
                                  │
              유사도 0.95 이상 → "원본"   /   그 아래 → "대체 후보"
```

| 항목 | 내용 |
| --- | --- |
| 임베딩 모델 예시 | CLIP·SigLIP 계열, 패션 특화 FashionCLIP. 우리 상품으로 파인튜닝하면 정확도 상승 |
| 학습 방식 | 대조 학습: 같은 상품 사진끼리는 가깝게, 다른 상품은 멀게 |
| 원본 판정 | 유사도 임계값 + 브랜드·로고·디테일 확인. 임계값은 실험으로 정한다 |

### 5-3. 취향 점수

```
취향 벡터 T = Σ (가중치ᵢ × 모은 룩 속 옷 임베딩ᵢ) / Σ 가중치ᵢ   (+ 구매·반품·리뷰 보정)
후보 점수 = 코사인 유사도(T, 후보 임베딩)  →  0–100%로 변환
```

- **주 데이터는 사용자가 모은 룩**(갤러리 업로드, 핀·인스타 공유)이다. 캡처는 "진짜 갖고 싶다"는 가장 솔직한 신호이고, 사용자가 이미 쌓아둔 데이터라 입력 부담이 없다.
- 모은 룩 사진은 룩 분해로 아이템별로 나눈 뒤 임베딩한다. 옷이 없는 사진은 제외한다.
- 보정: 구매·유지는 가중치 +, 반품은 −, 리뷰 키워드는 소재·핏처럼 사진으로 알기 어려운 선호를 더한다. 최근에 모은 룩일수록 가중치를 높인다.
- 마이페이지에는 모은 룩에서 뽑은 기장·실루엣·색·소재 비율을 "저장한 룩으로 본 내 취향"으로 보여준다.
- 발전 방향: 단일 평균 대신 **여러 취향 벡터**(출근룩, 주말룩)로 나누기, 클릭·구매 데이터로 학습한 추천 모델로 교체

### 5-4. 사이즈 추천

```
1. 상품 실측표 → {어깨 44, 가슴 52, 총장 48, …} (비전 LLM으로 추출)
2. 내 기준 실측 → 잘 맞았던 옷들의 실측 범위
3. 사이즈별 거리 계산 → 가장 가까운 사이즈
4. 보정: 같은 브랜드 "작아서 반품" 이력 → 한 치수 위로
5. 신뢰도가 낮으면 "두 사이즈 사이예요" 라고 솔직하게 표시
```

### 5-5. 예산 조합: 다중 선택 배낭 문제

```
아이템 i마다 선택지 {원본, 후보1, 후보2, 후보3} 중 하나
목표: Σ 점수 최대화
조건: Σ 가격 ≤ 예산
점수 = 취향 점수 + (원본이면 원본 보너스) + (포인트 아이템 원본이면 추가 보너스)
       - (쇼핑몰 수가 늘면 배송비 페널티)
```

- 아이템 3–5개, 선택지 4개면 최대 1,024가지라 **전수 탐색으로 충분**하다.
- 아이템이 많아지면 동적 계획법(DP)으로 푼다.

### 5-6. LLM 오케스트레이터

| 항목 | 내용 |
| --- | --- |
| 역할 | 요청 해석, 도구 호출 계획, 결과 종합, 이유 설명, 실측표·속성 추출 |
| 도구 목록 예시 | `detect_items`, `search_products`, `score_taste`, `recommend_size`, `optimize_budget`, `add_to_cart`, `place_order`, `watch_price` |
| 안전장치 | `place_order`는 가드레일을 반드시 거치고, 사용자 승인 토큰이 없으면 실행 불가 |
| 입력 원칙 | 상품 설명·리뷰는 "데이터" 영역으로 분리해 전달하고, 그 안의 지시는 따르지 않도록 설계 |
| 비용 관리 | 계산은 도구가 하고, LLM 호출은 요청당 2–3회로 제한. 작은 모델과 큰 모델을 용도별로 나눠 쓴다 |

## 6. 결제 실행과 상시 에이전트

### 6-1. 결제 방식별 처리

| 방식 | 처리 흐름 |
| --- | --- |
| 한 번에 결제 | 가드레일 → 쇼핑몰별 주문 API 병렬 호출 → 일부 실패 시 사용자에게 알리고 나머지 유지 또는 전체 취소 선택 |
| 골라서 결제 | 체크한 아이템만 위와 같이 처리, 나머지는 감시 목록에 등록 |
| 장바구니 담기 | 쇼핑몰 장바구니 API 호출. 결제 없음 |
| 가격 내려가면 사기 | 감시 목록 등록 → 스케줄러가 매시간 가격 확인 → 목표가 이하 + 재고 있음 + 조건 동일 → 가드레일 → 주문 → 알림 |

### 6-2. 권한 구조 (AIR Agent 개념)

```
사용자 ──(위임: 한도 30만 원, 허용몰 5곳, 30일 유효)──▶ 에이전트 권한 증명서
                                                         │
에이전트 ──(주문 + 권한 증명서)──▶ 쇼핑몰 ──(검증)──▶ 신원·범위 확인 후 주문 수락
```

- 권한은 **범위(한도, 허용몰)와 유효 기간**이 있고, 사용자가 언제든 철회할 수 있다.
- 모든 에이전트 행동은 감사 로그에 남겨 사용자가 확인할 수 있게 한다.

### 6-3. 운영에서 신경 쓸 것

| 항목 | 내용 |
| --- | --- |
| 멱등성 | 같은 주문 요청이 두 번 들어가도 한 번만 결제되게 멱등키를 쓴다 |
| 부분 실패 | 쇼핑몰 3곳 중 1곳만 실패할 수 있다. 사용자에게 선택권을 준다 |
| 재고 경쟁 | 결제 직전 재고·가격을 다시 확인한다 |
| 관측성 | 단계별 응답 시간, 오류율, LLM 비용을 대시보드로 감시 |
