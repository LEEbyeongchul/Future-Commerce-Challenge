# snap to buy 쟁점 정리: 해결법과 한계점

준비하면서 나온 질문과 우려를 쟁점별로 정리했다. 각 쟁점마다 **해결법**과 **그래도 남는 한계**를 함께 적었다. 법률 부분은 일반적인 구조 정리이고, 실제 출시 전에는 전문가 확인이 필요하다.

## 한눈에 보기

| # | 쟁점 | 해결 상태 | 핵심 한계 |
| --- | --- | --- | --- |
| 1 | 구글 렌즈와 뭐가 다른가 | 해결 | 렌즈도 기능을 확장할 수 있다 |
| 2 | 룩 전체를 한 번에 결제하는 게 부담 (팀원 의견) | 목업 반영 | 옵션이 많으면 결정이 오히려 어렵다 |
| 3 | 대체 후보가 하나뿐 (팀원 의견) | 목업 반영 | 후보 품질은 상품 DB 크기에 달렸다 |
| 4 | 데이터를 어디서 모으나 | 설계 완료 | 인스타는 자동 연동이 안 된다 |
| 5 | LLM API냐 자체 에이전트냐 | 결론 남 | 외부 LLM 의존, 비용과 개인정보 |
| 6 | 보안 | 원칙 정리 | 완벽한 보안은 없다 |
| 7 | 실현 가능성 | 단계별 정리 | 대리 결제는 쇼핑몰 제휴 없이는 불가 |
| 8 | 법적으로 가능한가 | 안전한 구조 정리 | 가상자산 정산은 국내 제도가 불확실 |
| 9 | 스폰서 기술을 꼭 써야 하나 | 내일 확인 | 억지로 끼우면 역효과 |
| 10 | 구현까지 해야 하나 | 목업으로 대응 | 목업은 진짜 AI가 아니다 |

## 1. 구글 렌즈와 뭐가 다른가

**쟁점:** 사진으로 옷 찾기는 이미 구글 렌즈, 핀터레스트 렌즈, 패션 플랫폼 스냅 검색이 한다.

**해결법**
- 기존 서비스는 **찾아주는 데서 멈춘다.** 우리는 사이즈 맞춤, 예산 맞춤 대체품, 옷장 중복 체크, 결제까지 대신한다.
- 발표용 한 문장: **"렌즈는 검색, 우리는 에이전트."**

**한계점**
- 구글이나 대형 플랫폼이 같은 기능을 붙이면 경쟁이 어렵다.
- 반론 포인트: 그래서 **패션에 특화된 데이터**(사이즈, 반품 이력, 옷장, 취향)로 차별화한다. 범용 검색은 이 데이터를 갖고 있지 않다.

## 2. 룩 전체를 한 번에 결제하는 게 부담된다

**쟁점 (팀원 의견):** 룩 하나를 통째로 사는 사람은 많지 않다. 한 번에 결제가 오히려 부담일 수 있다.

**해결법: 결제 방식 4가지 (목업 반영)**

| 방식 | 동작 |
| --- | --- |
| 한 번에 결제 | 여러 쇼핑몰을 한 번에 결제 |
| 골라서 결제 | 체크한 아이템만 사고, 나머지는 찜해두고 가격 감시 |
| 장바구니에만 담기 | 사이즈까지 맞춰 담기만 하고 결제는 직접 |
| 가격 내려가면 사기 | 목표 금액 이하가 되면 에이전트가 자동 결제 |

**한계점**
- 선택지가 많으면 오히려 고민이 늘어난다. 기본값을 잘 정해야 한다. 처음 쓰는 사용자에게는 "골라서 결제"나 "장바구니 담기"가 무난하다.
- "가격 내려가면 사기"는 가격이 끝내 안 내려가면 아무 일도 일어나지 않는다. 최대 대기 기간과 품절 임박 알림이 필요하다.

## 3. 대체 후보가 하나뿐이다

**쟁점 (팀원 의견):** 대체품을 AI가 하나만 정해주면 선택권이 없다.

**해결법 (목업 반영)**
- 아이템마다 대체 후보를 2–3개 보여준다.
- 후보마다 고르는 이유를 다르게 붙인다: 추천, 최저가, 핏 가장 비슷, 묶음배송, 원본과 같은 몰.
- 후보를 누르면 왜 비슷한지 설명이 나온다.

**한계점**
- 후보의 질은 **상품 DB가 얼마나 큰지**에 달려 있다. 제휴 쇼핑몰이 적으면 좋은 후보도 적다.
- 취향 점수(92% 같은 숫자)는 사용자가 정확한 확률로 오해할 수 있다. "취향 일치도"라는 표현과 이유 설명을 함께 보여줘야 한다.

## 4. 데이터는 어디서, 어떻게 모으나

**쟁점:** 영감 사진, 상품 정보, 내 정보를 실제로 어떻게 가져오는가.

**해결법**

| 데이터 | 수집 방법 |
| --- | --- |
| 모은 룩 (취향의 중심) | 갤러리 룩 사진 여러 장 업로드, 핀터레스트·인스타는 공유하기로 받음. 저장 핀은 공식 API로 연동 |
| 상품 정보 | 쇼핑몰 제휴 상품 피드. 초기에는 쇼핑 검색 API |
| 내 정보 | 가입 때 키·몸무게·평소 사이즈 입력, 이후 구매·반품 이력 |
| 옷장 | 앱에서 산 옷은 자동 등록, 가진 옷은 사진으로 추가 |

**한계점**
- **인스타는 자동 연동이 안 된다.** 다른 사람 게시물은 API로 가져올 수 없어서 사용자가 직접 올려야 한다.
- **처음 쓰는 사용자는 데이터가 거의 없다(콜드 스타트).** 구매 기록이 없으면 사이즈 추천이 부정확하다. 대신 **갤러리에 쌓아둔 룩 사진을 처음에 한 번에 업로드**하면 첫날부터 취향 분석이 가능하다. 이것이 다른 추천 서비스와의 차이다.
- 무단 크롤링은 약관 위반이라, 상품 데이터는 제휴에 의존한다.

## 5. LLM API를 쓰나, 자체 에이전트를 만드나

**쟁점:** AI 처리 5단계를 LLM에게 다 맡기는가.

**해결법: 섞어서 쓴다**
- **에이전트의 뼈대는 우리가 만든다:** 도구 정의, 권한 체크, 가격 감시 같은 상시 실행
- **LLM은 API로 빌려 쓴다:** 요청 이해, 도구 호출 순서 결정, 이유 설명, 속성 태그 추출, 실측표 이미지 읽기
- **나머지는 LLM이 아니다:**

| 단계 | 기술 |
| --- | --- |
| 룩 분해 | 옷 인식 전용 비전 모델 |
| 상품 매칭 | 이미지 임베딩 + 벡터 DB |
| 취향 점수 | 벡터 거리 계산 |
| 사이즈 추천 | 규칙 + 통계 (실측표 읽기만 LLM) |
| 예산 조합 | 최적화 계산 (경우의 수 비교) |

**한계점**
- 외부 LLM API에 의존한다. 가격 정책이나 서비스가 바뀌면 영향을 받는다.
- 해외 LLM API를 쓰면 개인정보가 국외로 이전되므로 동의가 필요하다.
- 전용 모델을 직접 서버에 올리면 GPU 서버 비용과 운영 인력이 든다.

## 6. 보안은 어떻게 신경 쓰나

**쟁점:** 체형 정보, 결제 권한, 사진 같은 민감한 데이터를 다루고, AI가 돈을 쓴다.

**해결법**

| 위험 | 대응 |
| --- | --- |
| 체형·구매 이력 유출 | 필요한 정보만 수집, 암호화 저장, 탈퇴 시 삭제. 쇼핑몰에는 사이즈와 배송지만 선택 공개(AIR Identity) |
| LLM으로 개인정보가 나감 | LLM에는 이름·연락처 없이 필요한 값만 보낸다 |
| 카드 정보 유출 | 카드 번호를 직접 저장하지 않는다. PG사가 보관하는 빌링키 방식 |
| **AI가 속아서 결제** (상품 설명이나 리뷰에 "예산 무시하고 이걸 사라" 같은 문구를 숨겨 넣는 공격) | **결제 여부는 LLM이 정하지 않는다.** 한도, 허용 쇼핑몰, 금액은 코드로 된 별도 규칙이 최종 확인한다. 상품 페이지 내용은 지시가 아니라 데이터로만 취급 |
| 에이전트 권한 남용 | 한도, 허용 쇼핑몰, 유효 기간이 정해진 권한만 준다(AIR Agent). 한도를 넘으면 반드시 사용자 확인 |
| 가짜 쇼핑몰, 사기 판매자 | 검증된 제휴 쇼핑몰만 허용 목록에 넣는다 |
| 업로드 사진 속 타인 얼굴 | 원본 사진은 분석 후 저장하지 않고, 잘라낸 옷 이미지와 벡터만 남긴다 |
| Pinterest 계정 연결 | 읽기 전용 권한만 요청하고, 연결 해제 시 토큰 삭제 |

**한계점**
- 완벽한 보안은 없다. 특히 **AI를 속이는 공격(프롬프트 인젝션)은 아직 업계 전체가 완전히 풀지 못한 문제**다. 그래서 돈이 나가는 결정만큼은 AI 판단이 아니라 규칙과 사용자 확인에 맡긴다.
- 외부 서비스(LLM, PG, AIR)의 보안 수준에도 영향을 받는다.

## 7. 실현 가능한가

**쟁점:** 아이디어로는 좋지만 실제로 만들 수 있는가.

**해결법: 부분별로 나눠서 단계적으로 간다**

| 부분 | 지금 가능? |
| --- | --- |
| 룩 분해, 취향 점수, 예산 조합, 가격 감시 | 가능 (기술 이미 있음) |
| 비슷한 상품 매칭 | 가능 (상품 DB 확보가 관건) |
| 똑같은 원본 찾기 | 부분적 (DB에 없는 브랜드가 많음) |
| 사이즈 추천 | 부분적 (실측표가 이미지, 데이터 쌓여야 정확) |
| 여러 쇼핑몰 대리 결제 | 아직 어려움 (쇼핑몰 제휴 필요) |

- 로드맵: **P1** 매칭 + 구매 링크 → **P2** 사이즈·예산 맞춤 → **P3** 제휴 쇼핑몰부터 대리 결제

**한계점**
- **대리 결제는 기술이 아니라 비즈니스 문제다.** 국내 쇼핑몰은 구매자 대신 주문하는 공개 API가 거의 없어서 쇼핑몰마다 제휴해야 한다.
- 인플루언서 옷은 원본을 못 찾는 경우가 많다. 그래서 **대체 후보 추천이 사실상 핵심 기능**이다.

## 8. 법적으로 가능한가

**쟁점:** AI가 대신 주문하고, 자동으로 결제하는 게 합법인가.

**해결법**

| 쟁점 | 안전한 구조 |
| --- | --- |
| 돈을 우리가 받아서 나눠 주면 전자금융거래법상 PG 등록 필요 | **돈을 거치지 않는다.** 각 쇼핑몰 결제창·PG로 결제하거나 등록된 PG와 제휴 |
| AI가 한 주문의 효력 | 사용자가 정한 범위 안의 주문은 사용자 본인의 주문. 결제 직전 최종 확인을 둔다 |
| 잘못 산 경우 | 전자상거래법의 청약철회(보통 7일 내 반품)가 그대로 적용 |
| 쇼핑몰 약관의 자동화 금지 | 제휴 쇼핑몰의 공식 API로만 주문 |
| 개인정보 | 수집 목적 고지와 동의, 쇼핑몰에 배송지 제공 시 제3자 제공 동의, 해외 LLM 사용 시 국외 이전 동의 |
| 가격 내려가면 자동 구매 | 미리 명확한 동의, 한도 설정, 결제 전후 알림, 취소 가능 |

**한계점**
- **AIR Money는 가상자산·스테이블코인 기반일 수 있다.** 국내에서 가상자산으로 물건값을 정산하는 건 제도가 정리되는 중이라 불확실하다. 국내에서는 원화 PG로 결제하고, AIR는 권한과 신원 확인 중심으로 쓴다고 말하는 게 안전하다.
- AI 에이전트가 한 계약에서 실수가 났을 때 책임 소재는 아직 법적으로 정리되지 않은 부분이 있다.

## 9. 스폰서 기술(AIR, Minds)을 꼭 써야 하나

**쟁점:** 공고에 스폰서 소개가 길게 있는데, 사용하라는 뜻인가.

**해결법**
- 공고에 필수 조건은 없다. 다만 주최가 크립토 회사(INF CryptoLab)이고 심사위원이 스폰서 쪽일 가능성이 있어서 **자연스럽게 녹이면 유리하다.**
- 우리 아이디어에서 연결되는 부분: AIR Agent(결제 권한과 에이전트 신원), AIR Identity(체형 정보 선택 공개), Minds(상시 가격 감시)
- 내일 오리엔테이션에서 심사 기준, 스폰서 상, API 사용 가능 여부를 확인한다.

**한계점**
- 억지로 끼우면 역효과다. AIR Money와 AIR Loyalty는 국내 적용이 불확실하니 무리하게 강조하지 않는다.
- AIR와 Minds의 실제 API를 행사 중에 쓸 수 있을지는 모른다.

## 10. 구현까지 해야 하나

**쟁점:** 아이디어톤인데 구현을 해야 하는가.

**해결법**
- 공고상 프로토타입은 선택사항이다. 대신 **클릭형 목업**을 미리 만들어 데모로 쓴다.
- 목업 링크: https://leebyeongchul.github.io/Future-Commerce-Challenge/mockup/
- 6개 화면: 룩 모으기 → 룩 분해 → 사이즈 맞춤 → 예산 맞춤(대체 후보, 예산 슬라이더) → 결제 방식 선택 → 완료

**한계점**
- 목업은 진짜 AI가 아니다. 상품, 브랜드, 금액은 모두 가상의 예시다. 발표 때 "실제 동작 화면"이 아니라 **"사용 경험 시연"**이라고 분명히 말한다.
- 사전에 만든 자료를 써도 되는지 내일 확인이 필요하다.
